The browser sends KPI requests to the local API. The API validates them and reads or writes PostgreSQL. The frontend currently points to http://127.0.0.1:8000; this is local development configuration, not a deployed environment.

General data schema

User
Owns dashboard data (currently one shared demo user).
MetricCatalog
Defines metric name, category, unit, and aggregation.
Goal
Stores the user's target, period, and metric reference.
Fact
Stores timestamped observed values and their source.
Connection
Designed to store external-provider connection/token metadata.
SyncRun
Designed to record connector sync status and results.

A KPI shown in the UI combines a Goal with its MetricCatalog details and latest Fact. DashboardLayout is also modeled for future saved widget configuration.

Set up and verified

  • Plain HTML/CSS/JavaScript dashboard with KPI cards and create/edit/delete form.
  • FastAPI health endpoint and KPI CRUD routes.
  • PostgreSQL persistence through SQLAlchemy and psycopg.
  • Live browser CRUD flow was validated against the API.
  • Tests use a disposable PostgreSQL schema per run; latest suite: 19 passed.
  • Mock API exists as a development fallback; current API URL is hardcoded locally.

Still missing / next

  • Real user accounts, authentication, and per-user data access.
  • External provider authorization, data import, scheduling, retries, and sync UI.
  • Production/staging configuration and a deployed hosting environment.
  • Frontend/API configuration that selects the API URL by environment.
  • Complete browser verification of loading and API-error states.

Current scope

This is an alpha/MVP foundation, not yet a production service. Manual KPI CRUD and the backend data model are in place. Connector-related tables are groundwork only: no real connector currently imports user data.

Near-term priorities: explain the backend/services and integrations; finish UI state checks; make API configuration deployment-ready; then design manual-versus-connector KPI behavior.
